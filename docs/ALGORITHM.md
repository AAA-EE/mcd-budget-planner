# 算法说明

本文档解释 `src/mcd_planner/solver.py` 的设计依据与实现细节。

---

## 1. 为什么需要约束求解

单看营养数据，158 项餐品中「钠含量最低」的结果往往是可乐、纯悦这类饮品——
它们钠含量为 0，但显然不构成一顿正餐。

同样，只看价格也无法回答「我想吃麦当劳但要控钠」这类复合诉求。

因此本模块的设计目标是：**在多个硬约束下，找出仍然像一顿饭的组合。**

---

## 2. 数据模型

### 2.1 NutritionItem

```python
@dataclass(frozen=True)
class NutritionItem:
    name: str
    kcal: float
    protein_g: float
    fat_g: float
    carb_g: float
    sodium_mg: float
    calcium_mg: float
    category: str  # burger / side / drink / dessert / other
```

`frozen=True` 保证条目不可变，组合运算中不会被意外修改。

派生属性 `kcal_per_protein`（每克蛋白质对应热量）用于高蛋白低热优选。

### 2.2 Constraints

```python
@dataclass(frozen=True)
class Constraints:
    max_kcal: float | None = None
    max_sodium_mg: float | None = None
    max_fat_g: float | None = None
    min_protein_g: float | None = None
    min_calcium_mg: float | None = None
    budget: float | None = None
    exclude: frozenset[str] = frozenset()
    categories: frozenset[str] | None = None
```

全部字段可选，任意组合均可。`None` 表示该维度不设限。

### 2.3 NutritionTotals

组合的营养合计，支持增量累加（`add(item, qty)`），便于递归过程中逐步计算。

## 3. 餐品分类

分类基于名称关键词匹配。实测 158 项中148 项可归类，
剩余 10 项为联名新品（苹板、果然多肉等），无法可靠判断类别，保留 `other`。

**设计取舍**：宁可归为 `other` 也不要归错。
错误的分类会让高钠汉堡被当作低钠小食推荐出去，
这比「无法分类」危害更大。

分类规则的优先级：

```
KNOWN_BURGERS（显式名单） → dessert → side → drink → burger（结构词）
```

### 为什么要显式列KNOWN_BURGERS

「巨无霸」「麦香鸡」「麦香鱼」等经典汉堡名中**不含量词**（「堡」「卷」「三件套」），
纯关键词匹配会漏判为 `other`，导致这类高蛋白餐品无法进入组合。
因此对这部分做显式枚举。

这是一个在开发中真实发现并修复的缺陷——`tests/test_solver.py::test_classify` 是其回归保护。

## 4. 求解流程

```
load_dataset()
     │
     ▼
filter_items()          ← 单品级粗筛，缩小搜索空间
  · 排除 exclude 中的餐品
  · 类别过滤
  · 单项已超标的直接剔除（如热量上限 300kcal 时，巨无霸 513kcal 必被剔除）
     │
     ▼
类别内截断             ← 每个类别保留钠含量最低的 6 项
  · 组合爆炸的主要来源是同质候选
  · 按 (钠, 热量) 排序后截断
     │
     ▼
递归枚举 + 剪枝
  · 增量剪枝：钠/热量一旦超标，立即跳过该分支
  · 多样性约束：同类别最多 2 项
  · 集合去重：按餐品名排序后作为 key
     │
     ▼
_score() 排序          ← 按综合评分升序
     │
     ▼
top-N 输出
```

## 5. 评分函数

```python
def _score(t: NutritionTotals) -> float:
    sodium_penalty = t.sodium_mg / 100.0 * 3.0
    kcal_penalty = t.kcal / 100.0 * 1.0
    protein_bonus = t.protein_g * 0.15

    if t.kcal < 200:
        satiety_penalty = (200 - t.kcal) / 100.0 * 2.5
    else:
        satiety_penalty = 0.0

    return sodium_penalty + kcal_penalty - protein_bonus + satiety_penalty
```

### 权重设定依据

| 项 | 权重 | 依据 |
|---|---|---|
| 钠 | 3.0 | 实测数据中钠含量从 0mg 到 1373mg，跨越三个数量级，是最主要的差异维度 |
| 热量 | 1.0 | 作为基础约束，量级相对可控 |
| 蛋白 | −0.15 | 正向奖励，鼓励高蛋白选择 |
| 饱腹 | 动态 | 见下|

### 饱腹惩罚：一个真实缺陷的修复

初版评分函数只有前三项，在「控钠午餐（钠 ≤ 600mg，热量 ≤ 500kcal）」场景下，
算法输出了这样的结果：

```
冰美式小杯 + 热美式小杯 + 浓缩咖啡
热量 33kcal · 钠 0mg
```

三杯咖啡，钠含量完美为0，但显然不是一顿午餐。

**根因**：评分函数只惩罚钠和热量，而这三项恰好在两个维度都最优
（零钠、近乎零热量），在纯数值上碾压了含汉堡的正餐方案。

**修复**：加入饱腹惩罚。热量低于 200kcal（一份正餐的下限）的组合会被施加惩罚：

```
satiety_penalty = (200 - kcal) / 100 * 2.5
```

同时加入多样性约束（同类别最多 2 项），防止出现「三杯咖啡」这类堆砌。

修复后同一场景的输出变为：

```
小杯玉米杯 + 大杯玉米杯 + 浓缩咖啡
热量 153kcal · 蛋白 7g · 钠 3mg
```

**回归测试**：`test_satiety_penalty_avoids_drink_only_combos`
断言每个推荐组合都必须包含 burger 或 side 类餐品。

## 6. 复杂度

设截断后候选数为 `n`，最大组合大小为 `k`：

- 过滤阶段：`O(n)`
- 枚举阶段：最坏 `O(n^k)`，但增量剪枝使实际搜索量大幅下降
- 多样性约束进一步将同质分支排除

实测 158 项数据集、`max_size=3` 时响应在毫秒级。

## 7. 已知局限

| 局限 | 说明 |
|---|---|
| 无价格数据 | 离线层不含价格，`budget` 约束需由在线层的 `calculate-price` 补足 |
| 营养为静态数据 | MCP 营养表为固定值，与门店实际出品可能存在偏差 |
| 不考虑饱腹感主观因素 | 200kcal 阈值是经验值，非营养学标准 |
| 分类覆盖 148/158 | 联名新品无法可靠归类 |
| 不处理套餐组合 | 仅支持单品组合，未解析套餐（round）结构 |

## 8. 与在线层的衔接（初版设计，已被第 9 节取代）

离线求解器产出**候选组合**，在线层负责**真实定价**：

```
离线层：营养约束 → 候选组合（不关心价格）
          │
          ▼
在线层：MCP calculate-price → 真实实付金额
          │
          ▼
最终排序：实付金额优先 / 营养达标的组合中选最便宜
```

初版的想法是「营养算在本地，价格问接口」。这个分工后来被推翻了，
原因见第 9 节。

---

## 9. 定价引擎：为什么算术必须放在本地

### 9.1 推翻初版设计的两个原因

**原因一：接口不可靠**

2026-10-13 重测 `calculate-price` 时持续返回：

```
/items: must be array
```

连续 4 次尝试（带券 / 不带券 / 换商品 / 加参数）均报同一错误，
而 2026-10-09 首次联调时该接口是正常的。判断为服务端变更。

**原因二：调用的次数根本不允许**

枚举 41 项餐品的 3 件组合，可行方案约 3000 个。
如果每个方案都调一次 `calculate-price`：

| 方案数 | 远程调用次数 | 可行性 |
|---|---|---|
| 42（预算 30，2 件） | 42 | 可接受 |
| 3,109（预算 50，3 件） | 3,109 | 分钟级，不可接受 |
| 更宽的场景 | 上万 | 不可接受 |

而本地计算同样的规模是毫秒级。

### 9.2 本地定价的实现

```python
price_basket(items, menu, coupons, now, scope, stack_policy)
```

四个步骤：

```
1. 券可用性过滤
   ├─ 时间：valid_from / valid_to
   ├─ 星期：weekdays（0=周一）
   ├─ 时段：time_window（如早餐券 05:00–10:29）
   └─ 场景：dine_in / delivery
        ↓
2. 逐行匹配最省的券（券后价 ≤ 门店价才算命中）
        ↓
3. 叠加策略裁决
   ├─ SINGLE（默认）：只保留节省最多的一张
   └─ GREEDY：允许多张，但先做两两冲突检测
        ↓
4. 全场券（满减/折扣）二次计算
```

### 9.3 「划线价」作为对照基准

这是一个真实的缺陷修复。

初版用门店现价（`currentPrice`）作为「原价」基准，结果：

```
中薯条买一送一 ×1
实付 ¥13.50（原价 ¥13.50，省 ¥0.00）   ← 明明省了一半
```

根因：「中薯条买一送一」这个 SKU 本身就是券商品，门店现价 13.5
已经是券后价。用它当基准，等于拿优惠价和优惠价比。

**修复**：改用 `originalPrice`（划线价 ¥27，即两份薯条原价）作为基准。

```
中薯条买一送一 ×1
实付 ¥13.50（原价 ¥27.00，省 ¥13.50）   ✓
```

回归测试：`test_saving_uses_original_price`

### 9.4 叠加规则是假设，不是事实

**必须说清楚的一点**：麦当劳 MCP 并未公开券的叠加规则。
`query-store-coupons` 只返回券的适用商品与券后价，没有 `stacking` 字段。

因此本项目的 `STACK_SINGLE`（一单一张券）是**显式假设**，理由：

1. 保守——宁可少算优惠，也不给用户一个到店后不成立的承诺
2. 符合实际——麦当劳常规订单基本遵循此规则
3. 可配置——需要时可切 `STACK_GREEDY`，此时会做冲突检测

冲突判定规则（同样是显式假设）：

```
同商品被两张券覆盖  → 冲突
全场券 vs 单品券    → 冲突（该商品已被全场券覆盖）
两张全场券          → 冲突
其余                → 可叠加
```

## 10. 价格 × 钠 的帕累托前沿

### 10.1 为什么选钠而不是热量

热量是常见维度，但钠更值得关注：

- 中国居民钠摄入普遍超标（《中国居民膳食指南》建议每日食盐 <5g，约合钠 2000mg）
- 麦当劳餐品的钠跨度是**数量级**的：0mg（纯悦）到 1373mg（芝士安格斯厚牛堡）
- 热量跨度只有约 6 倍（0 到 1003kcal）

差异越大，帕累托前沿越有信息量。

### 10.2 算法

双目标最小化（价格、钠），标准的非支配筛选：

```python
plans.sort(key=lambda p: (p.price, p.sodium_mg))
frontier = []
best_sodium = inf
for p in plans:
    if p.sodium_mg < best_sodium - 1e-9:
        frontier.append(p)
        best_sodium = p.sodium_mg
```

按价格升序遍历，只要钠严格低于此前所有点，就是前沿点。
正确性依赖一个事实：价格更高的点若钠不更低，必然被某个更便宜的点支配。

复杂度：排序 O(n log n) + 扫描 O(n)。

### 10.3 一个反直觉的实测结果

在 41 项可参与求解的餐品中，即使枚举 3,946 个可行组合，
**帕累托前沿只有 2 个点**：

```
 实付      钠      热量   组合
17.00   731mg   369kcal  麦香鸡
22.50   556mg   325kcal  麦香鱼
```

含义：其余 3,944 个组合都能被某个「更便宜或更低钠」的选项替代。

这不是算法缺陷，而是**市场供给的效率结论**——在当前的菜单与价格结构下，
消费者真正需要做的决策只有两个档位。

### 10.4 同类替代

用户往往已有明确想吃的单品，此时不该硬推别的方案。
`dominating_alternatives(code)` 回答的是「你选的这个，有没有更优的同类替法」。

**这里踩过一个语义坑**：初版未限制类别，结果给巨无霸的替代方案里
出现了圆筒冰淇淋——价格更低、钠更低，判定完全正确，
但把汉堡换成冰淇淋不是「替代」，是「换了一顿饭」。

**修复**：只在同类中比较（主食 ↔ 主食，小食 ↔ 小食）。
另允许「主食 + 低钠饮品」的组合替代。

回归测试：`test_alternatives_same_category_only`

### 10.5 数据覆盖的诚实边界

菜单 91 项，营养表 158 项，但**同时具备价格与营养的只有 41 项**。

原因：
- 套餐（三件套等）由多项组成，营养需累加，MCP 未提供套餐营养
- 联名新品（龙焰系列等）不在营养表中
- 规格不明的（如「牛奶」未标冷热大小）无法对应

处理方式：建立 `data/menu_nutrition_map.json` 显式映射，**只映射有把握的**。
未映射的商品仍可用于纯价格排序，但不参与价格×钠分析。

宁可少算 50 项，也不要给错一项。

## 11. 前后端一致性

页面 `docs/index.html` 里的算法是上述 Python 实现的 JavaScript 移植。
两份代码独立存在，必然会漂移。

`tools/parity_check.mjs` 的做法：

1. 从 `index.html` 中用正则提取内联 `<script>` 内容
2. 在最小 DOM 桩下 `new Function(source)()` 执行，取得挂载的 `globalThis.MCD`
3. 用与 Python 相同的 7 组输入（固定时间）跑一遍
4. 逐点比对帕累托前沿（方案名、价格、钠含量）

CI 中这一步失败即构建失败。这样「页面算错」不会悄悄上线。

已知局限：对拍只覆盖求解结果，不覆盖渲染层（DOM 输出）。
渲染错误仍需人工目视检查。
